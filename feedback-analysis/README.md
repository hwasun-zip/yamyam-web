# 피드백 자동 분류 (LLM)

설문 서술형 의견을 직접 읽고 주제별로 묶던 작업을 Claude로 자동화하고, 사람의 분류와 비교해 실제로 믿고 쓸 수 있는지 검증했다.

## 왜 만들었나
v1, v2를 배포할 때마다 서술형 의견을 하나씩 읽고 주제별로 묶어 다음 개선의 우선순위를 정했다 (v1 18건, v2 8건). 이 방식에는 두 가지 문제가 있었다.

1. **의견이 늘수록 시간이 그만큼 늘어난다.** 버전마다 같은 작업을 처음부터 반복한다.
2. **분류 기준이 흔들린다.** v1과 v2의 주제 목록이 달라 버전 간 비교가 어렵고, 한 의견에 여러 요청이 섞이면 놓치기 쉽다.

## 방법
1. v1, v2 README에서 쓴 주제를 하나의 목록(11개)으로 합치고, 주제마다 정의를 적었다.
2. Claude에 주제 정의만 주고, 의견마다 해당 주제를 모두 고르게 했다. 근거가 된 구절도 함께 받는다. **사람의 분류 결과는 보여주지 않았다.**
3. 사람의 분류(정답)와 비교해 일치율, 정밀도, 재현율을 계산했다.
4. 불일치한 응답만 모아 누가 놓쳤는지 직접 판정했다.

## 결과 (서술형 26건)

| 지표 | 결과 |
| --- | --- |
| 응답 단위 완전 일치 | 92% (24/26) |
| 재현율 (사람이 붙인 주제를 LLM도 찾은 비율) | **100%** |
| 정밀도 (LLM이 붙인 주제 중 사람도 붙인 비율) | 96% |
| 처리 시간 | 77초 (건당 3초) |

### 불일치 2건: 모두 사람이 놓친 요청

| 응답 | LLM이 더 찾은 주제 | 근거 구절 |
| --- | --- | --- |
| v1 | 사진·아이콘 | "음식점 리뷰 사진을 긁어모아서 썸네일 처럼 사진이 있었으면 좋겠다" |
| v2 | 개인 취향·회원 | "사용자 정보가 추가되면 좋을 것 같아요!" |

두 건 모두 한 의견에 여러 요청이 섞여 있었고, 수작업 분류에서는 앞의 요청만 집계하고 뒤의 요청을 놓쳤다. 판정 후 기준으로는 26건 모두 LLM 분류가 맞았다.

### 같은 우선순위 결론에 도달
자동 생성된 표에서도 v1 1위는 **지역 확대(44%)**, v2 1위는 **음식 종류(75%)**로, 수작업으로 내린 "가장 큰 불만이 지역에서 메뉴로 옮겨갔다"는 결론이 그대로 재현됐다.

### 버려지던 의견 5건을 따로 모음
목록에 없는 요청은 `other`로 받게 해, 수작업 때 어느 주제에도 들어가지 않아 집계에서 빠졌던 의견 5건을 새 주제 후보로 모았다.
- 음식점 배너 2열 배치 (레이아웃)
- 날씨 바꿔 보기를 빼고 '오늘 추천'만 남기기
- 추천 식당 수 늘리기
- 앱테크 서비스와 연계
- 여러 곳 대신 한 곳만 추천하기

## 운영 방식의 변화

| | 이전 | 이후 |
| --- | --- | --- |
| 1차 분류 | 전체 의견을 직접 읽고 분류 | LLM이 분류 (근거 구절 포함) |
| 걸린 시간 | 약 20~30분 (읽기, 분류, 재검토 포함. 기억 기준) | 77초 + 불일치 2건 검토 |
| 사람이 보는 것 | 26건 전부 | 불일치와 새 주제 후보만 |
| 다음 버전 | 주제 목록부터 다시 정리 | CSV만 바꿔 다시 실행 |

## 한계
- 표본이 26건으로 작다.
- 정답 중 1건(v1 '지역 확대' 8번째)은 응답 단위 기록이 없어, v2에서 "내 위치 주소 표시"를 지역 문제의 해결책으로 넣은 점을 근거로 추정해 배정했다.
- 주제 목록은 사람이 만들었다. LLM은 정해진 목록 안에서 분류하고, 목록 밖 요청은 후보로만 제시한다.
- 실행할 때마다 결과가 조금 달라질 수 있다. 위 수치는 1회 실행 기준이다.
